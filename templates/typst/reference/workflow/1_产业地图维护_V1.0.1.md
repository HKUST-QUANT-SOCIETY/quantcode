**当前最终负责人：项目总负责人**

## 一、阶段定义

产业地图维护是整个研究工作流的入口。

本阶段负责维护团队对产业世界的统一分类，确保团队能够持续回答以下问题：

- 目前长期关注哪些产业领域；
    
- 每个产业领域被拆分到什么层级；
    
- 某个赛道、产业链环节或技术模块应当归属于哪里；
    
- 哪些内容已经研究，哪些正在研究，哪些尚未覆盖；
    
- 每项已有研究应挂接到哪个产业节点；
    
- 哪些新产业变化值得进入地图；
    
- 哪些旧节点需要合并、拆分、重命名或停止维护。
    

本阶段的直接任务是维护一份统一、稳定、可扩展的产业分类和研究状态底表，为后续的研究主题筛选、产业链拆解、标的池建立和研究资产归档提供共同入口。

---

## 二、阶段起点与终点

### 2.1 阶段起点

出现以下任一情况时，启动一次产业地图维护：

1. 新增一项尚未进入地图的产业、赛道或技术方向；
    
2. 已有研究发现原有产业结构划分不合理；
    
3. 同一对象在不同材料中使用多个名称；
    
4. 一个产业节点过大，需要拆分；
    
5. 多个产业节点实际高度重叠，需要合并；
    
6. 某项技术从阶段性专题逐渐发展为稳定产业环节；
    
7. 某项原有产业或技术已经失去独立研究意义；
    
8. 新完成的研究项目需要挂接至长期产业地图；
    
9. 定期复核发现节点长期未更新或状态失真。
    

### 2.2 阶段终点

一次产业地图维护只有在以下事项全部完成后才算结束：

- 新增、拆分、合并、重命名、调整层级、暂停或归档建议已经形成；
    
- 相关节点的定义和上下位关系已经明确；
    
- 变更已经过总负责人确认；
    
- 主表已经更新；
    
- 变更记录已经保存；
    
- 受影响的研究项目、公司和研究资产链接已经同步调整；
    
- 不再存在因本次变更产生的重复节点、孤立节点或失效链接。
    

未完成正式审批和关联关系同步的修改，只能保留为“待确认建议”，不能直接进入正式产业地图。

## 三、目标

建立并持续维护团队唯一有效的产业分类体系，使所有研究项目、产业链节点、技术模块、公司和研究资产都能挂接至明确位置

### 第一，分类对象明确

地图中的每个条目必须被定义为以下一种类型：

- 一级领域；
    
- 二级赛道；
    
- 三级产业；
    
- 技术模块；
    
- 阶段性专题标签。
    

不同类型不得在同一层级中混用。

例如：

- “AI与数字基础设施”可以是一级领域；
    
- “光互联”可以是二级赛道；
    
- “光模块”可以是三级产业；
    
- “CPO”可以是技术模块；
    
- “1.6T放量”可以是阶段性专题标签。
    

不能把“光互联”“CPO”“AI算力资本开支上修”并列为同一层级的长期产业分类。

### 第二，节点范围明确

每个节点必须说明：

- 包含哪些产品、技术或业务；
    
- 不包含哪些相邻领域；
    
- 上一级节点是什么；
    
- 是否存在下一级节点；
    
- 与哪些技术模块或专题标签相关。
    

### 第三，研究状态明确

团队及管理层应能够直接看出某个节点当前处于：

- 尚未覆盖；
    
- 准备研究；
    
- 正在研究；
    
- 已形成基础覆盖；
    
- 已形成完整研究；
    
- 持续跟踪；
    
- 暂停维护；
    
- 已归档。
    

### 第四，责任和时间明确

每个已经进入研究或跟踪状态的节点，应有：

- 当前负责人；
    
- 最近更新时间；
    
- 最近一次研究项目；
    
- 下一次复核时间。
    

### 第五，所有研究资产可以挂接

行业报告、产业链图、标的池、公司档案、投资命题和行业 Skill，均应挂接至至少一个正式产业节点。

## 四、输入

本阶段不接受只有口头描述的修改需求。所有产业地图变更必须基于以下输入之一。

### 4.1 《长期产业地图主表》

这是本阶段的核心输入，也是团队唯一有效的产业分类数据源。

建议以数据库或结构化表格管理，不以 Word、PPT 或独立思维导图作为正式主表。

每一行代表一个产业节点。

### 必填字段

| 字段                | 内容要求                 |
| ----------------- | -------------------- |
| node_id           | 节点唯一编号，创建后原则上不得修改    |
| parent_id         | 上一级节点编号；一级领域可为空      |
| level             | L1、L2、L3、Module或Topic |
| node_type         | 一级领域、二级赛道、三级产业、技术模块、专题标签 |
| standard_name     | 唯一标准名称               |
| aliases           | 常见别名、旧称、英文名和缩写       |
| definition        | 节点的一句话定义             |
| included_scope    | 明确包含的产品、技术和业务        |
| excluded_scope    | 明确不包含的相邻内容           |
| research_status   | 当前研究状态               |
| owner             | 当前维护或研究负责人           |
| latest_update     | 最近更新时间               |
| next_review       | 下一次计划复核时间            |
| related_projects  | 关联研究项目编号             |
| related_assets    | 关联报告、Skill、标的池等资产    |
| related_companies | 关联公司主表链接或数量          |
| active_status     | 正式、待确认、暂停、归档         |
| notes             | 其他说明                 |

### 4.2 《产业节点变更申请单》

任何成员发现地图结构问题时，应提交变更申请。

申请单至少包括：

- 申请日期；
    
- 申请人；
    
- 当前涉及节点；
    
- 建议操作类型；
    
- 建议名称；
    
- 建议层级；
    
- 建议父节点；
    
- 修改原因；
    
- 支持材料；
    
- 对现有项目和资产的影响；
    
- 是否需要紧急处理。
    

操作类型统一为：

- 新增；
    
- 拆分；
    
- 合并；
    
- 重命名；
    
- 调整层级；
    
- 修改定义；
    
- 暂停；
    
- 归档；
    
- 恢复。
    

### 4.3 已结项研究项目

每个行业项目结项时，应检查是否产生以下地图变更：

- 新产业环节；
    
- 新技术模块；
    
- 新的上下位关系；
    
- 原有节点定义调整；
    
- 新的别名；
    
- 已失效分类。
    

项目负责人应在结项材料中增加“产业地图更新建议”。

### 4.4 外部变化候选清单

该清单用于记录可能影响产业地图的新信息，例如：

- 新技术标准形成；
    
- 新产品类别出现；
    
- 产业链价值重心转移；
    
- 原有技术路线被替代；
    
- 新商业模式形成；
    
- 监管使某一行业边界发生变化。
    

候选信息只能作为变更依据，不能由自动化系统直接写入正式主表。

## 五、主要动作

### 5.1 检查现有节点

维护人首先检查：

- 是否已有同义节点；
    
- 是否已经存在上位或下位节点；
    
- 是否属于长期产业结构，还是短期专题；
    
- 是否与技术模块混用；
    
- 是否会造成现有资产重复挂接；
    
- 是否需要新增节点，而不是仅增加标签。
    

### 5.2 判断变更类型

#### 新增节点

适用于：

- 形成了相对独立的产品、客户、技术和竞争格局；
    
- 能够单独建立标的池；
    
- 具有持续研究价值；
    
- 不能被现有节点合理容纳。
    

#### 拆分节点

适用于：

- 原节点覆盖范围过大；
    
- 下属部分具有不同需求、技术和竞争格局；
    
- 原节点已经无法支持有效分工和标的映射。
    

#### 合并节点

适用于：

- 两个节点长期研究内容高度重复；
    
- 无法形成独立标的池；
    
- 市场和产业实践中并不存在稳定区分；
    
- 分开维护会造成重复劳动。
    

#### 重命名节点

适用于：

- 原名称不准确；
    
- 行业通行名称发生变化；
    
- 不同材料中名称不统一；
    
- 原名称容易与技术路线或公司产品混淆。
    

#### 降级为技术模块或专题标签

适用于：

- 条目无法形成独立产业链和标的池；
    
- 主要作用是描述一种技术方案；
    
- 只在特定阶段具有研究意义；
    
- 可以跨多个产业节点使用。
    

#### 暂停或归档节点

适用于：

- 行业已经失去当前研究价值；
    
- 技术路线基本退出；
    
- 团队短期不再投入资源；
    
- 原节点已被其他节点替代。
    

归档节点不得直接删除，应保留历史引用。

### 5.3 分析变更影响

每次正式变更前，必须检查：

- 哪些研究项目受到影响；
    
- 哪些公司需要重新映射；
    
- 哪些报告、Skill和投资命题需要更新链接；
    
- 是否导致历史数据不可比；
    
- 是否影响现有负责人和跟踪任务。
    

### 5.4 审批变更

审批分为两级。

#### 一般变更

包括：

- 增加别名；
    
- 修改文字定义；
    
- 补充关联资产；
    
- 更新研究状态；
    
- 更新负责人或时间。
    

由维护人直接更新并纳入变更记录，总负责人定期抽查。

#### 结构性变更

包括：

- 新增正式产业节点；
    
- 拆分；
    
- 合并；
    
- 调整层级；
    
- 删除或归档；
    
- 将技术模块升级为产业节点。
    

由总负责人审核，确认执行后知会上级管理层。

### 5.5 更新主表和关联对象

变更确认后，应一次性完成：

- 更新产业地图主表；
    
- 生成变更记录；
    
- 更新研究项目引用；
    
- 更新公司节点映射；
    
- 更新研究资产链接；
    
- 检查是否产生孤立节点；
    
- 通知受影响成员。

## 六、输出规格

### 6.1 更新后的《长期产业地图主表》

这是本阶段最重要的正式输出。

正式主表应具备：

- 唯一版本；
    
- 唯一保存位置；
    
- 权限管理；
    
- 变更时间记录；
    
- 可导出为 CSV 或 Excel；
    
- 可被 Sentinel 或其他工具读取；
    
- 可生成树状图和状态看板。
    

### 6.2 《产业节点变更记录》

每次正式修改形成一条记录。

字段至少包括：

- change_id；
    
- 修改日期；
    
- 修改人；
    
- 审批人；
    
- 操作类型；
    
- 修改前内容；
    
- 修改后内容；
    
- 修改原因；
    
- 受影响节点；
    
- 受影响项目；
    
- 关联迁移是否完成。
    

### 6.3 《待确认问题清单》

对于暂时不能确定的分类问题，不应强行写入正式地图，而应进入待确认清单。

内容包括：

- 问题描述；
    
- 涉及节点；
    
- 当前候选方案；
    
- 所需补充证据；
    
- 负责人；
    
- 复核时间。
    

### 6.4 《关联关系更新记录》

记录本次变更是否已经同步至：

- 项目；
    
- 公司；
    
- 标的池；
    
- 研究报告；
    
- 行业 Skill；
    
- 投资命题；
    
- 动态跟踪任务。

## 七、相关负责人

### 7.1 总负责人

负责：

- 决定一级产业和核心二级赛道的总体结构；
    
- 审批结构性变更；
    
- 处理无法统一的分类争议；
    
- 确认长期产业覆盖是否符合团队规划；
    
- 定期主持产业地图复核。
    

### 7.2 产业地图维护人

短期由总负责人维护，后续可设置固定资产管理员。

负责：

- 接收变更申请；
    
- 检查主表；
    
- 准备变更建议；
    
- 更新正式数据；
    
- 维护变更记录；
    
- 检查关联关系；
    
- 提醒长期未更新节点。
    

维护人无权独立批准结构性变更。

### 7.3 项目负责人和研究成员

负责：

- 在研究过程中发现分类问题；
    
- 提交有依据的变更建议；
    
- 在项目结项时完成地图更新检查；
    
- 确认自己负责的研究资产已经挂接到正确节点。
    

### 7.4 自动化工具

自动化工具负责提出建议，不承担最终分类责任。

可执行：

- 别名识别；
    
- 重复节点检测；
    
- 可能的上下位关系建议；
    
- 孤立节点检测；
    
- 失效链接检测；
    
- 长期未更新提醒；
    
- 新资料与现有节点匹配。

## 八、验收标准

本阶段验收按照以下标准执行。

### 8.1 结构完整性

- 所有正式节点均有唯一编号；
    
- 所有非一级节点均有有效父节点；
    
- 不存在无法归类的孤立节点；
    
- 不存在循环上下位关系；
    
- 同一层级的分类依据基本一致。
    

### 8.2 名称一致性

- 每个对象只有一个标准名称；
    
- 其他称呼进入 aliases 字段；
    
- 英文缩写、中文名和旧称可以互相检索；
    
- 不存在同义重复节点。
    

### 8.3 范围明确性

- 每个正式节点均有定义；
    
- 包含范围与排除范围明确；
    
- 技术模块、产业环节和专题标签得到区分；
    
- 新成员可以仅依据定义判断一项材料应挂接到哪里。
    

### 8.4 关联完整性

- 已结项项目均挂接至产业节点；
    
- 标的池和公司能够追溯至产业节点；
    
- 行业报告和 Skill 有明确归属；
    
- 结构变更后的原有链接已经迁移。
    

### 8.5 状态真实性

- 研究状态与实际进度一致；
    
- 负责人和更新时间有效；
    
- 长期未更新节点得到标记；
    
- 已暂停或归档节点不再被误认为当前活跃项目。
    

### 8.6 可维护性

- 所有变更都有记录；
    
- 历史节点不会因改名而失去引用；
    
- 主表能够被机器读取；
    
- 不需要依赖某一名成员的个人记忆理解结构。

## 九、自动化设计

### 9.1 适合自动化的动作

可以开发“产业地图维护助手”，完成：

- 从新研究材料中抽取产业、技术和公司名称；
    
- 将新名称与 aliases 进行匹配；
    
- 检测可能重复的节点；
    
- 建议上一级节点；
    
- 检测产业与技术路线的混用；
    
- 提醒长期未更新节点；
    
- 检查项目和资产是否存在失效链接；
    
- 生成待审核的变更建议。
    

### 9.2 必须人工确认的动作

以下动作不得由 AI 自动写入正式主表：

- 创建一级产业领域；
    
- 新增正式二级赛道；
    
- 拆分或合并产业节点；
    
- 判断一个技术是否升级为独立产业；
    
- 归档长期产业节点；
    
- 改变团队长期研究范围。
    

### 9.3 推荐实现形式

第一阶段不必立即开发复杂 Agent，可以先采用：

1. 结构化产业地图主表；
    
2. 标准变更申请模板；
    
3. 用于名称标准化和重复检查的 Prompt；
    
4. 人工审批后写入主表。
    

当产业节点数量、研究项目和公司映射明显增加后，再开发专用 Agent 与 Sentinel 接口。

---

## 十、维护频率

产业地图采用事件触发和定期复核相结合的方式。

### 事件触发

以下情况发生后应立即提出更新：

- 新行业项目启动或结项；
    
- 发现重大新技术路线；
    
- 产业链出现明显重构；
    
- 原有分类影响项目分工；
    
- 新标的无法合理挂接；
    
- 原节点出现明显重复。
    

### 定期复核

建议每月进行一次轻量复核，检查：

- 新增候选；
    
- 重复节点；
    
- 未更新节点；
    
- 未挂接资产；
    
- 待确认问题。
    

每季度进行一次结构复核，讨论：

- 一级产业是否需要调整；
    
- 二级赛道是否需要拆分或合并；
    
- 团队长期覆盖是否发生变化；
    
- 哪些技术专题已经形成稳定产业节点。
    

---

## 十一、异常处理

### 11.1 无法判断层级

暂时作为“待确认节点”，不得直接进入正式地图。由总负责人在下一次复核会议中决定。

### 11.2 一个对象跨多个产业

设定一个主归属节点，同时通过关联字段连接其他节点。不得为了多重归属重复创建同一对象。

### 11.3 技术路线与产业高度重合

判断其是否能够形成独立的需求、产品、参与者和标的池。如果不能，则保留为技术模块。

### 11.4 历史材料使用旧名称

不修改历史原文，但将旧名称写入 aliases，并将历史材料挂接至当前标准节点。

### 11.5 节点已经失效

将状态改为归档，并说明替代节点或失效原因。原则上不物理删除。

---

## 十二、本阶段不负责的事项

产业地图维护阶段不负责：

- 决定具体研究项目优先级；
    
- 制定项目详细研究计划；
    
- 完成技术和产业链深度研究；
    
- 建立公司完整档案；
    
- 对标的作出估值和投资判断；
    
- 决定实际投资或组合配置。
    

这些工作分别由后续的研究主题筛选、技术与产业链拆解、公司全覆盖、团队假设与估值讨论、投资命题形成等阶段完成。

---

## 十三、本阶段完成定义

产业地图维护阶段完成，应达到以下状态：

> 团队拥有一份唯一有效、层级清晰、名称统一、范围明确、状态真实并可被机器读取的产业地图；所有既有研究项目和研究资产均可挂接至明确节点；任何新增产业、技术或专题均有标准入口；所有结构变化均经过审批并保留历史记录。
