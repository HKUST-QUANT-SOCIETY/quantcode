项目分析 · MIMOCODE vs OPENCODE

MimoCode 在 OpenCode 之上改进了什么

小米 MiMo 团队 fork OpenCode 之后，把"短期助手"改造成"长任务工程"—— 持久化记忆、自动 checkpoint、Goal 评判、Compose 工作流，再加上语音和自学习。 这份文档拆解每一项加法。

1总体结论

OpenCode 是一个短交互式 AI 编程 agent——一次会话内完成一件事，会话结束信息就散了。 MimoCode 把它改造成长任务工程平台：会话之间能记住上下文、上下文满了能自动重建、任务有树状结构、可以同时跑几个 subagent、停止之前还要一个独立的 judge 模型来评判"是不是真的完成了"。

用一句话总结：OpenCode 解决"如何让 AI 写代码"，MimoCode 解决"如何让 AI 持续地、可靠地写代码"。

官方表述

MiMoCode 的 README 在 "Relationship to OpenCode" 一节写道：保留所有 OpenCode 核心能力（multi-provider / TUI / LSP / MCP / plugins）， 在其之上 新增持久化记忆、智能上下文管理、subagent 编排、goal 驱动的自主循环、compose 工作流、以及通过 dream/distill 的自我改进。

2持久化记忆系统

OpenCode 的会话状态主要在内存里。SQLite 存的是 session 元数据和消息，但项目级别的"知识"没有专门的载体——每次新开会话，agent 要重新读代码、重新理解架构。

MimoCode 引入了一套四层文件结构，专门保存跨会话的知识，并用 SQLite FTS5 全文索引：

MEMORY.md
项目级长期知识：架构决策、命名规范、关键路径——session 之间共享
checkpoint.md
当前 session 的结构化快照，由专门的 checkpoint-writer subagent 自动维护
notes.md
agent 用的临时草稿区，可以丢一些短期信息
tasks/<id>/progress.md
每个任务自己的日志，断点续跑时读这个

会话 resume 时这些文件被自动注入上下文。这是从"AI 助手"到"团队成员"的关键差异——你不需要每次都给它讲一遍"我们用 SolidJS 不用 React"。

为什么这件事重要

OpenCode 的范式是"每次对话从零开始 + 一次性把上下文喂够"。 MimoCode 的范式是"agent 在项目里安家"。后者更接近一个真实工程师的工作方式——你不会每天早上把所有项目知识重学一遍。

实现上的代码组织（packages/opencode/src/memory/）：

memory/
├── service.ts        # 统一入口
├── reconcile.ts      # 合并/去重逻辑
├── fts.sql.ts        # SQLite FTS5 schema
├── fts-query.ts      # 全文检索
└── paths.ts          # 文件路径约定

3智能上下文管理

所有 agent 工具的天敌都是 context window 满了之后怎么办。OpenCode 的处理比较朴素——截断或者让用户手动开新会话。MimoCode 在这里下了三个工夫：

3.1 自动 checkpoint

系统根据当前模型的 context window 占用率，自动判断什么时候应该 snapshot。不需要用户手动按"保存"。

3.2 上下文重建

当 context 接近上限时，MimoCode 不是简单截断，而是用以下材料重新组装一个新的 working context：

  1. 最新的 checkpoint.md（结构化任务状态）
  2. MEMORY.md 中相关的项目知识（FTS5 检索）
  3. 当前 task 的 progress.md
  4. 最近 N 条原始消息（保留语义连续性）

结果是 agent 可以"接着干"，而不是"重新开始"。

3.3 预算化注入（budgeted injection）

注入新上下文时有一个 token budget，并按 importance ranking 决定哪些内容进、哪些不进。 这是工程化的关键——不是"全部塞进去"，而是"按价值排序后塞够为止"。

这解决了什么真实问题

4树状任务追踪

OpenCode 的 task 是扁平的列表——你提一个需求，它做一个 task。MimoCode 引入了树状任务系统：

T1   实现 risk-gate skill
├── T1.1   定义 risk-profile JSON Schema
├── T1.2   实现策略代码静态分析
│   ├── T1.2.1   识别仓位计算逻辑
│   └── T1.2.2   识别杠杆使用
├── T1.3   实现回测调用
└── T1.4   接入 CI Gate

每个节点都有自己的 progress.md，和 checkpoint 系统自动联动——会话 resume 时知道你做到哪一棵子树的哪一个叶子。

这对我们有什么实际价值？它直接对应了 QuantCode 设计文档里的"任务拆分"方法论。我们不需要再设计一套 task hierarchy，MimoCode 已经有了。

和我们设计文档的映射

设计文档 §2.1 写的是"把大任务拆成无状态子任务，子任务间用确定性 JSON schema 通信"。 树状任务 = 拆分；JSON Schema = 我们写在 schemas/；checkpoint 联动 = idempotent 重启。 三件事在 MimoCode 里都齐了。

5Subagent 编排

OpenCode 已经有了 subagent 的初步概念（比如 @general、自定义 subagent），但 MimoCode 把它做完整了：

  • 按需创建：primary agent 在需要时动态生成 subagent，不是事先注册
  • 共享上下文：subagent 继承当前会话的上下文，不需要重新喂
  • 并行执行：多个 subagent 可以同时跑（关键！）
  • 生命周期追踪：每个 subagent 都有 ID，可以查询状态
  • 取消能力：跑错了能 kill 掉，不会一路炸到底
  • 后台执行：长任务可以放后台，不占主对话

实际场景：一个 compose:plan skill 跑完之后，可以同时启动 3 个 subagent 分别去做 3 个独立子任务，并在它们都完成后汇总。

对我们的意义

研报生成场景里非常用得到—— 一个 subagent 拉财务数据、一个去 RAG 检索研报、一个画图，三件事并行， 最后由 primary agent 合成 PDF。这是 MimoCode 直接送给我们的并发模型。

6Goal 与 Judge 模型

这一节是 MimoCode 最有"研究气质"的设计。

问题：autonomous agent 在长任务里有一个臭名昭著的失败模式——"optimistic stop"， 也就是模型觉得"我做完了"然后停下来，但其实没完成。OpenCode 里这种事经常发生。

MimoCode 的解决方案：

  1. 用户用 /goal "完成因子评估并通过验收" 设置一个停止条件
  2. Agent 想要停止时，系统先调用一个独立的 judge model
  3. Judge 拿到整个对话历史，独立判断："这个 goal 真的满足了吗？"
  4. Judge 说 yes → 停；说 no → agent 必须继续

这个设计的精髓在于判断者和执行者分离。执行者天然乐观（它做了很多工作，倾向于说"够了"）， 判断者只看结果（没有付出沉没成本，更客观）。

这是我们设计文档"程序化验收"的灵魂版本

7Compose Mode：specs-driven 工作流

OpenCode 的工作模式是 build（写代码）和 plan（只读分析）二选一。 MimoCode 引入了第三种 primary agent —— compose，它把整个软件开发周期编成了一套可调用的 skills：

brainstorm  →  plan  →  execute  →  review  →  tdd
                                                   ↓
                                  verify  ←  debug
                                     ↓
                                   merge

每一步都是一个 SKILL.md：

brainstorm
把模糊需求拆成清晰的 spec
plan
spec 转工程计划，包含完整文件结构、任务清单、测试方案
execute
按 plan 实施
review
独立 reviewer 模型做 code review
tdd
测试先行
debug
失败时的诊断 skill
verify
最终验收
merge
合并到主分支
parallel
多 subagent 并行调度
worktree
用 git worktree 做隔离开发
subagent
显式启动子 agent
report
结构化报告产出
feedback / ask
主动征求人类反馈
new-skill
由 agent 自己写新 skill
这对我们是天降甘霖

QuantCode 设计文档 §2 的"任务拆分 + 程序化验收"在 compose mode 里已经被实现一遍了。 我们要做的不是重新发明这套工作流，而是在 compose 之上加业务 skill—— 比如 quant:risk-gate 直接复用 compose:verify 的验收骨架，只换业务阈值。

8Dream 与 Distill：自我改进

这是 MimoCode 最具有"未来感"的两个命令。

8.1 /dream — 知识沉淀

扫描最近会话的 trace，把反复出现的、值得长期持有的知识提取到 MEMORY.md，并删除过期条目。 本质上是 agent 的"睡眠记忆固化"——白天工作累积的临时记忆，晚上整理成长期记忆。

8.2 /distill — 工作流封装

检查最近的手动操作，识别重复的工作流，把高置信度的候选打包成新的 skill / subagent / command。 也就是说，agent 可以自己写新的 skill。

例子：你前三周手动跑了 5 次"读财报 → 提取关键数字 → 写 markdown summary"，distill 会问你："要不要我把这个流程做成一个 skill financial-summary？" 你说 yes，它就生成 SKILL.md 写入 .mimocode/skills/。

对量化团队的杠杆

我们最重的工作是把"研究员的隐性工作流"转成"机器可执行 pipeline"。 Distill 提供了一条"边用边沉淀"的路——研究员只管手工跑业务，agent 在后台观察、提议、封装。 这是从"显式编码所有 skill"到"涌现 skill"的范式转换。

9Voice：语音输入

OpenCode 没有原生语音。MimoCode 做了一套流式语音输入：

  • VAD（语音活动检测）：TenVAD，按停顿切片
  • ASR：MiMo ASR（小米自家），逐段转写到输入框
  • 触发：/voice 命令
  • 依赖：sox（命令行音频工具）

对量化团队是不是必需？未必。但有两个场景可能有用：

  1. 研究员开会时口述"我要看一下今天宁德时代的新闻流和情绪"，agent 直接接住
  2. 跑长任务时不想打字，可以语音追加指令

10Max Mode：best-of-N + judge

这是 MimoCode 的实验特性，藏在 experimental.maxMode 配置里。

思路：对于关键决策，并行让 N 个模型实例独立给答案，然后一个 judge 模型选出最好的一个。 本质上是把"模型采样不稳定"问题用集成来缓解。

开销
token 成本 ×N（默认 3-5），延迟约 ×1.2（并行）
收益
关键节点正确率显著提升，尤其在边缘 case 上
适用场景
架构决策、code review、生成验收报告等"错了代价大"的任务
不适用
日常补全、简单工具调用
对量化场景的应用

风控门禁场景是典型适用—— 风控判断错了代价远大于多花一些 token。 我们的 risk-gate skill 可以默认开启 Max Mode， 其他低风险的 skill（如 RAG 检索结果摘要）保持单实例。

11Provider 整合：MiMo Auto 与 Claude Code 一键迁移

OpenCode 启动时需要用户自己配置 provider 和 API key，对新用户门槛高。MimoCode 做了三件事降低门槛：

11.1 MiMo Auto 免配置 channel

首次启动可以选 MiMo Auto（free for limited time），匿名 channel，零配置就能跑。 背后用的是小米自家模型（MiMo 系列）。

11.2 从 Claude Code 一键迁移

如果用户之前用 Claude Code，MimoCode 提供 "Import from Claude Code" 选项， 一键迁移已有的 Anthropic 认证。这对从 Claude Code 切换过来的人是零摩擦体验。

11.3 Custom Provider in TUI

OpenAI 兼容的 provider 可以在 TUI 里直接添加，不用编辑配置文件。

对我们的策略含义

团队成员各自有自己习惯的 LLM provider（Claude / GPT / DeepSeek / 国产模型）。 MimoCode 的多 provider 设计意味着我们不需要锁定一家—— Lead 用 Claude Opus，组员用 DeepSeek，CI 用便宜的 batch 模型，都在同一个 MimoCode 框架里跑。

12.3 我们要做的真正的事

把整个项目重新定位为"在 MimoCode 上写量化 skills"，而不是"造一个量化平台"。 我们的 IP 是业务知识的编码（JSON Schema、阈值、Typst 模板、prompt 工程）， 不是工具链本身。

13小结与取舍

MimoCode 在 OpenCode 之上的改进，本质是把"短交互助手"升级为"长任务工程平台"。 持久化记忆、自动 checkpoint、Goal/Judge、Compose mode 这四件事是核心； Dream/Distill/Voice/Max Mode 是锦上添花。

取舍上，MimoCode 也付出了代价：

  • 复杂度增加：相比 OpenCode 的"一次会话一次 task"，新用户需要理解 memory / checkpoint / task tree / subagent 这套体系
  • 磁盘占用：MEMORY.md / checkpoint.md / notes.md 等文件需要管理
  • 调试难度：subagent 并行 + 自动 checkpoint 之后，"为什么 agent 做了 X" 更难追溯
  • 厂商绑定风险：MiMo Auto / MiMo ASR 这些免费 channel 依赖小米自家服务
一句话总结

"OpenCode 给你 agent，MimoCode 给你 agent 的工程化生命周期。" 对 QuantCode 而言，这意味着我们不用造工具链，只用造业务—— 把港科大量化协会的隐性流程，编译成 MimoCode 跑得动的 skills。
