# QuantCode 执行引擎源码内化与单循环决策

日期：2026-09-08。状态：用户已确认目标架构；迁移未完成。

功能与权限边界服从 `specs/FUNCTIONAL_SPEC.md`。本决策替代旧设计中“Python/LangGraph 必须独占核心推理编排”的实现约束，不改变 QuantCode 不承担领域业务真相的产品定位。

## 决定

QuantCode 以已经纳入本仓库的 OpenCode 执行引擎源码为基础，自行维护统一的任务执行机制。会话、模型调用、上下文、工具调用循环、子任务和用户交互属于 QuantCode 产品内部能力。用户不需要安装、登录或配置另一套 OpenCode 产品，也不需要了解 Python Runner 与桌面 Agent 的区别。

Python 保留组织服务、能力适配与确定性检查，不再为新任务运行第二套通用模型→工具→模型循环。Compose 表示 QuantCode 中的组织任务编排方式，与 plan/build 共用统一引擎，不是转交给独立 AI 产品的入口。子 Agent 可创建受约束的子会话，但必须使用同一执行引擎和父子任务契约；单循环不意味着禁止并行。

源码来源保持透明：保留原项目许可证、版权声明、第三方依赖许可和来源记录。工程内化不意味着宣称全部从零自研，也不以全仓字符串替换作为验收标准。

用户再次明确：能直接复用 OpenCode 或 MimoCode 的成熟实现就直接复用，不要求完全重写。新增实现前先核对仓库已有能力和调用链；现有会话、工具、模型、进程、锁、事件和恢复机制优先直接接入，只补 QuantCode 的组织身份、权限和产品适配。发现重复草稿时移除重复部分，不以“内化”为由另造一套底层机制。

### M1~M4 的复用边界

“内化”指产品归属和受控接线，不指重写 OpenCode 内核。四个阶段继续使用同一套已运行的 OpenCode 机制：

| 能力 | 复用的现有机制 | QuantCode 只补的部分 |
|---|---|---|
| 模型→工具→模型循环 | `SessionPrompt`、`SessionTools`、`Provider`、上下文压缩 | 身份、组能力目录、预算和 Gate 准入 |
| 会话、子任务和取消 | `Session`、`SessionRunState`、`Runner`、`BackgroundJob` | owner/root/parent 绑定、撤销重验和组织投影 |
| 事件、历史和恢复 | `EventV2`、原生消息/Part、快照、Git/LSP | QuantCode 事件类型、回执、legacy 只读边界 |
| 进程和文件 | Core `AppProcess`、Shell、FS、PTY、Flock、Ripgrep | 工作区授权、沙箱策略和副作用证据 |

因此 M1~M4 的源码改动可以落在 OpenCode 模块边界上，但只能是 QuantCode 的 policy hook、适配器或产品语义调整；不得复制循环、Provider、任务状态机或第二份持久化事实源。无法通过现有扩展点接入的需求，应记录为架构冲突，不能以重写内核解决。

## 目标职责

| 模块 | QuantCode 负责的行为 | 当前代码基础 |
|---|---|---|
| 桌面产品 | 任务、设置、编辑器、终端、模型选择、组织视图的统一交互 | `frontend/packages/app`、`desktop`、`ui`、`session-ui` |
| 统一执行引擎 | 会话创建/取消/继续、LLM、上下文压缩、工具调度、任务树和子 Agent | `frontend/packages/core` 与 `frontend/packages/opencode` 中实际运行的 session/tool/provider 模块 |
| 组织服务 | roster 身份、组 Memory、能力目录、Blackboard、契约、HumanGate 与 evidence | `quantcode`、`runner/memory`、`runner/blackboard.py`、`runner/permission_engine.py`、`tools`、`schemas` 中可复用实现 |
| 管理服务 | 跨成员状态汇总、目录发布、审批、GitGraph/Pop、受控部署 | 现有 Admin/GitHub/gateway 模块，补齐缺口 |
| 外部组件 | 因子、训练、风险、组合、回测、数据和报告业务 | 各组 canonical 仓库和服务；QuantCode 只接契约和适配器 |

执行位置与执行机制分开：统一引擎可以按工作区部署在可信宿主；远程个人文件/Shell 和组件工具可以通过受控连接运行。远程工具不因在服务器执行就必须再启动一个 AgentRunner。

## 源码内化的验收标准

1. **一份源码与发布流程**：现有 vendored 源码由 QuantCode 仓库维护、构建、测试和发布。不存在另装 OpenCode、运行上游线上页面或临时拉取未经审查最新源码的产品依赖。
2. **一套产品入口**：任务、设置、编辑器、终端、身份、组织页面和错误处理使用 QuantCode 语义；不要求用户在两个产品或两个聊天界面之间操作。当前全屏组织页需要进一步融入统一任务导航。
3. **一套模型配置**：URL + API Key 由受信任的宿主凭据服务保存，经统一 Provider 接口提供给执行引擎；不要求用户再为同一研究任务设置 QUANTCODE_API_KEY。模型专用服务如需推理，也使用统一受控接口并归属任务，不另起通用 Agent 循环。
4. **一套任务事实源**：同一任务的状态、消息、工具事件、取消、重试、用量与父子关系由统一引擎维护；组织索引是授权投影，不是第二个执行状态机。合法的并行子任务继承身份、预算和工作区约束。
5. **组织约束进入执行链**：身份来自 roster；工具发现与执行使用同一有效权限；原生文件/Shell、MCP 和子 Agent 都经过权限、工作区及 P-10 检查。Prompt/Skill 提示不能代替强制校验。
6. **可持续维护**：模块边界、测试、发布和依赖升级由 QuantCode 负责。上游改进通过有审查的提交引入，不能覆盖 QuantCode 的组织规则和产品配置。
7. **兼容性有边界**：内部旧包名、`.opencode` 路径和协议名可临时作为兼容接口；自有公共命名逐模块迁移并提供旧数据读入，第三方 API 与许可证中的 OpenCode 名称不任意改写。产品界面不展示这些内部兼容细节。

## 迁移阶段与退出条件

### M0：锁定规范和现状

同步功能规格、PRD、技术设计、UI 规格与缺口审计。保留“目标”与“现有实现”的区分。当前仓库已有完整源码，但还存在外层 Agent 强制转交 `run_agent`、Python 模型配置、旧 checkpoint 和 trace 桥；不能因源码在同仓就宣称迁移完成。

### M1：给统一执行引擎接上组织约束

先追踪 core 与 opencode 中实际被桌面使用的执行路径，避免同时修改两套候选 session 实现。复用现有 session/provider/tool/permission 扩展点，为任务创建、工具准入、副作用执行和子任务派生接入服务端权威身份。

保留 D-001~D-015 的行为约束。将原先只在 Python Runner 生效的复杂度分类、能力检索要求、P-10 文件面约束、预算与 Gate 检查覆盖到统一引擎的原生工具和 MCP 调用。审批必须绑定具体资源、参数和版本，不能将 UI 点击转化为广泛授权。

退出条件：未登录拒绝；组参数越权拒绝；普通身份不能执行生产部署；未冻结的 L2/L3 写入被拒绝；缺能力覆盖时确实先取得用户决定；原生 Shell/编辑/子 Agent 无法绕过组织约束。

### M2：切换新任务入口

在 M1 行为通过之后，新任务直接创建 QuantCode session，加载组 Skill、能力摘要和 Memory，按需调用组织服务/组件工具。移除首页与 slash command 中“必须立即调用 quantcode_run_agent”的强制模板。不删除 Python 组织服务。

退出条件：只配置一次 URL/API Key 即可完成真实“查询能力→读授权文件→调用一个已接入组件→记录结果”的任务；UI 提交、实时事件、停止和错误显示对准同一任务。计量覆盖主任务和子任务，不能出现隐藏的第二套模型配置。

### M3：统一状态、恢复与组织视图

Admin 的查询结果、Activity、方案、子 Agent、artifact 和知识候选从同一事件契约回流；服务端组织索引可汇总不同成员的授权任务。恢复时重新检查当前身份和资源授权。

旧 Python checkpoint 独立标记 legacy 并保留查询。仅在迁移期保留旧任务恢复适配器，旧任务不会静默作为新 session 重跑。恢复入口显式锁定执行器版本和原任务归属；不允许旧恢复入口接受新任务以绕过新链路。历史与审计数据不能被批量改名覆盖。

退出条件：新任务断线/重开后可继续；取消可终止实际执行；跨成员 Admin 汇总和审批已验证；旧记录可查，不误执行或重复副作用。

### M4：清理旧循环与工程命名

完成 M1~M3 后，移除新任务目录中的旧 run_agent 和 Python 通用子 Agent 执行入口，退役已完成兼容期的旧循环。保留 Memory/Blackboard/契约/服务适配；抽取与循环耦合的组织规则。逐模块清理过时的 OpenCode 专属设置、文案、包元数据和代码接口，更新文档与迁移工具。

不承诺“一次性全仓改名”；每次命名迁移需通过包依赖、SDK 生成、旧配置、历史、插件/技能路径以及桌面打包检查，外部协议有兼容期。

## 必须验证的场景

- 桌面单次模型配置可驱动新任务，断开或撤销凭据有明确状态，密钥不进 prompt、日志或 artifact。
- 身份退出/过期后新工具执行拒绝，迟到结果不泄露到另一身份；任意 group、workspace、role 参数不能提权。
- 主 Agent、子 Agent、原生文件/Shell、MCP 共享同一组织准入规则；只读查询不被无关审批阻塞。
- L2/L3 方案冻结与精确 Gate 恢复覆盖同一执行器；旧 checkpoint 回放不产生新任务或重复外部写入。
- 单一事件流可更新桌面 Activity、任务树、Admin 和证据索引；恢复、取消和错误不依赖事后解析最终消息。
- 所有业务计算来自权威组件；未接通组件继续如实显示 UNAVAILABLE/STAGING。
- QuantCode 桌面构建与安装不需要另一套 OpenCode；仅验证桌面窗口与产品发布流程，不增加手机范围。

## 已明确不做

不重新自造成熟的基础 Agent 循环；不把 Python 服务全部重写成 TypeScript；不把权限移动到提示词；不删除现有审计/知识/检查点；不把远程研究服务改成生产 shell；不重做领域算法；不将旧审计中的“给远程 Runner 补一份模型 key”作为目标架构的长期方案。
