# QuantCode 最终验收场景清单

日期：2026-09-08。性质：测试设计，不是执行报告。所有场景初始状态均为 **NOT_RUN**。

清单共 **220 条单项场景 + 12 条端到端旅程**。编号用于追踪，不代表已实现或已通过。

本文件是侧讨论新增的独立交付物；不修改主任务的代码、进度、阶段状态或上线开关，也不授权现在执行真实写入、故障注入、部署或测试。用于内化实现完成后的统一验收。

## 1. 范围、依据与口径

依据：

- [PRD](../PRD.md)：产品范围、八组用户流程、成功指标。
- [FUNCTIONAL_SPEC](../../specs/FUNCTIONAL_SPEC.md)：F-01~F-09、P-01~P-10、D-001~D-017 与最终权限边界。
- [内化与迁移方案](../decisions/QUANTCODE_RUNTIME_INTERNALIZATION_2026-09-08.md)：七项验收标准、M0→M4 和必须验证的七类场景。
- [桌面 UI 规格](../UI_DESIGN_SPEC.md)：桌面交互、状态、GitGraph 与 Admin 最新约定。
- [技术设计](../QuantCode_Design.md)：仅用于细化上述功能已承诺的任务树、编排、Schema、事件和恢复行为。

优先采用用户最新确认及功能规格的规范要求；日期较早的“已实现/未实现”台账不能定义测试预期。PRD 的产品 M1~M5 与内化 M0~M4 是两套编号。本文件不替主任务调整迁移顺序，也不能用测试清单存在证明某阶段完成。

**产品口径**：只有 QuantCode 一个桌面产品、一个新任务执行机制、一套模型配置。Python 保留组织服务和组件适配。业务算法与科学结论属于各组及 canonical components。

**明确范围**：仅桌面，不新增手机端。桌面常规窗口 1440×900、宽屏 1920×1080 核对 GitGraph 六列缩略卡片；缩小桌面窗口只检查内容可访问，不要求六列在任意极小窗口仍完整显示。Admin 使用「概览 / 任务 / 报告与产物 / 部署」。

**“所有场景”的边界**：覆盖当前规范中的产品能力、所有权边界、主要失败/并发/恢复路径及迁移兼容；不是穷举所有字符串和硬件组合。未来新增接口、工具、组件或平台必须扩展本表，不能借用旧通过结果。

**不新增业务需求**：不建立 QuantCode 自有回测/因子/组合/期权/报告平台，不测试投资收益是否优秀，不要求 L0/L1 固定讨论两轮。外部组件数值正确性由组件负责人验收；QuantCode 验证路由、输入输出、版本、契约、授权与如实展示。图谱历史窗口、diff 文件上限按正式范围声明测试，不把当前“30/100”等实现常数自动变成永久产品要求。

## 2. 如何执行和记录

### 2.1 标记

| 标记 | 含义 |
|---|---|
| P0 | 身份、数据、安全、任务执行、恢复或迁移阻断；失败不可宣布对应能力完成 |
| P1 | 产品功能完整性、桌面体验、运行可靠性；仍属最终验收，不是可省略项 |
| P2 | 质量测量或计划能力；不得假定通过，缺少指标/范围时明确待定 |
| D | 确定性组件/契约/集成测试，可用受控数据与故障替身 |
| E | Electron 桌面端到端；开发网页仅辅助诊断，不能替代安装包证据 |
| R | 真实组织身份、真实模型/组件/外部服务的联调 |
| F | 隔离环境故障/并发注入，绝不直接破坏真实成员数据 |
| S | 源码、构建、协议、发布包与依赖检查 |

D/E/F/R/S 可组合。一行包含多个失败变体时，每个变体必须有结果；不能只跑其中一个记整行通过。

### 2.2 每条执行记录

每个场景独立记录：`ID、需求来源、构建/commit/未提交补丁摘要、执行平台、角色/组、环境、前置数据、操作、预期、实际、证据位置、状态、缺陷ID、执行者、时间`。

状态只用：`NOT_RUN / PASS / FAIL / BLOCKED_EXTERNAL / NEEDS_SPEC / N/A`。`N/A` 需要需求负责人给出范围依据，不能因为“没实现”而 N/A。真实服务缺失记 `BLOCKED_EXTERNAL`；用替身验证失败处理可另记 D 通过，真实成功分支仍未通过。

证据代码：

- **U**：桌面截图/录屏、可访问性树、窗口尺寸、操作序列。
- **I**：脱敏请求/响应、实际身份和权限判定、事件游标；不保存真实 bearer 或密钥。
- **X**：执行器/子进程及模型请求追踪、取消信号、调用计数、父子任务与用量归属。
- **P**：执行前后文件/数据库快照、哈希、任务/方案/Gate/回执记录。
- **C**：权威组件的请求、响应、版本、artifact 与参考输入输出。
- **B**：构建/打包/安装/升级日志、依赖锁定信息、许可证清单。
- **Q**：性能原始样本、并发量、错误率、缓存状态和计时边界。

每行“证据”列列出最低证据；仅截图不能证明后端拒绝或未发生副作用。拒绝类用例需要 **U/I + P 或 X** 证明没有执行；无泄漏用例需要检查返回内容、事件、缓存和实际生成物。

## 3. 测试身份、数据和环境

### 3.1 身份矩阵

- 八组各一名 analyst：fundamental、factor、model、risk、strategy、options、infra、agent。
- 额外两名不同 actor 的同组成员 A1/A2；另一组成员 B1；组内 approver；组织 Admin；未认证用户。
- 多组 roster 身份仍由名册绑定本次单一组，桌面不提供自由选组。
- 准备同账号两个桌面窗口、同账号重登会话、不同成员独立机器/用户目录。
- 撤销公钥、角色降级、组变更、workspace/grant 变更、GitHub token 过期/错账号等情况，均在专用测试成员中进行。
- **同组共享知识不等于同组可以接管彼此私人任务。**普通任务归属与共享知识 ACL 分开测；Admin 只读查看他人任务不自动获得以原作者身份继续执行的权限。

### 3.2 资源矩阵

- 本人工作区、同组另一人的私有目录、其他组目录、授权共享目录、受限共享对象、生产目标。
- 已登记且接通组件、部分覆盖、无覆盖、下线版本、scaffold、未验证/不可用组件。
- 长期 Memory：已确认、候选、被替代、共享摘要、组私有；独立的 checkpoint/trace/task progress。
- 小/大文本、中文及空格路径、软链接逃逸、删除文件、二进制、损坏/缺失 artifact；所有数据均为测试样本。
- Git 仓库：直线、双分支、merge、多个父提交、同一提交多个 HEAD、空库、归档库、超一页提交、大 diff、rename/binary、权限撤销。
- 原生与旧 Python 历史：已完成、运行中断、等待 Gate、外部结果未知、旧版本/损坏记录、不可兼容版本。
- 模型接口：正常、无模型列表、401/403/429/5xx、断流、超时、缺 usage、格式错误；使用专用低权限测试 key，泄漏检测使用可识别 canary 值。

### 3.3 组合覆盖规则

1. AUTH/ACL 的登录与隔离基础场景对八组逐一执行；跨成员重点执行 A1→A2、A1→B1、A1→Admin、Admin→A1 降级；多组身份单独执行。
2. 所有可执行工具族至少覆盖：原生读、原生写、Shell、MCP 只读、MCP 副作用、前台子 Agent、后台子 Agent；同名动作经快捷命令、HTTP/SDK、旧入口、可达替代 API 再测绕过。
3. 在提交前、模型响应中、工具前、工具已开始、工具已完成但回执未落盘、结果已落盘但 UI 未收到七个时间点注入适用故障。
4. 六个领域链分别验收，Infra/Agent 验证工程任务；不强行给工程组虚构领域流程。
5. 每个实际发布支持的桌面 OS/架构运行安装和核心路径；具体矩阵在运行前锁定。仅支持一个平台时不能报告为三平台通过。
6. 同一条件的只读成功和写入拒绝都需要，避免用“全部拒绝”伪装权限正确。

## 8. 判定、外部依赖与待明确事项

### 8.1 最终通过规则

1. 上述适用场景均有逐项结果与证据；不以“全仓测试通过”代替真实旅程和权限证据。
2. 所有 P0 通过，所有 P1/P2 已执行并满足其已确定要求；任何正式延期必须有明确范围决定，不能暗中删用例。
3. D 替身通过只证明实现可按某契约工作。要求 R 的场景必须真实身份/外部服务联调，无法执行保持 `BLOCKED_EXTERNAL`。
4. 失败、取消、越权、部分完成、STAGING、无收益源、旧任务不兼容等负向状态必须正确；“正常场景全被拒绝”同样失败。
5. 实际发布支持的平台、最终安装包和未提交代码版本一致；测试运行中代码变化，应重验受影响项。
6. 已发生但结果未知的外部写入不得通过重试来“做绿”；必须核对证据和幂等。
7. 单列“平台软件完成度”和“外部真实服务联调完成度”。只要原目标要求的联调未完成，不能汇总为全部完成。

以下需要在执行前从正式配置/规格填写；本清单不替产品新增默认决定：

| 项 | 为什么需要 | 影响场景 |
|---|---|---|
| 实际发布 OS/CPU 架构、最小桌面窗口 | 决定安装/键盘/权限/升级和桌面尺寸矩阵 | BOOT、UI、LEG |
| token/时间/并发/深度/重试上限 | 不能任意造预算或把阈值缺失当通过 | MODEL、SUB、RUN、PERF |
| GitGraph 历史/分支/diff 读取范围与刷新时限 | 区分承诺完整性和明确的有限窗口 | GH、POP |
| 长任务取消策略及不可撤回组件语义 | 请求停止不必然等于外部动作被撤销 | SUB-04、RUN-09、DEP-05 |
| 跨成员索引一致性、刷新时限、知识发布延迟 | 当前某次碰巧查到不足以证明稳定共享 | MEM、KNOW、ADM、EVT |
| 组件权威版本与标准输入输出、真实测试目标 | 避免 fixture 冒充生产接通 | DATA、EXP、JOURNEY |
| 生产测试/回滚目标与受控服务账号 | 在隔离目标证明真适配，不误触真实业务 | DEP、JOURNEY-09 |
| 旧版本支持区间与恢复/升级/回退兼容矩阵 | 决定哪些旧任务可恢复、哪些仅只读 | LEG、RUN |
| P95 计时起止、样本量、冷热缓存、负载 | 防止统计口径不同却报达标 | PERF |

前置条件缺失时先记录 `NEEDS_SPEC` 或 `BLOCKED_EXTERNAL`，其他独立场景仍可执行。不得为了测试方便修改业务边界、重造组件或给普通账号提升权限。

### 8.3 建议最终执行批次

在实现完成后的统一验证期，按 **静态/契约→权限与故障→原生执行链→桌面功能→跨成员/真实服务→性能→安装升级与整体验收复核** 执行。批次不是新的迁移阶段，也不让 M2/M4 提前启用。产品代码、服务重启和真实外部副作用遵守主任务的环境约束与正式测试授权。

每批输出缺陷清单、失败原始证据和重验结果。最终报告必须保留未通过项、外部依赖、已知限制与实际验证范围，不能只报告测试总数。
